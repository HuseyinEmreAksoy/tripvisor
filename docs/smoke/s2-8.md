## BLOCKER B1 — OPFS persistence can never attach on web (degrades every load)

- Pill shows **"Local-only mode"** on every flag-on load despite `window.crossOriginIsolated === true` and the COOP/COEP middleware verified active.
- Issues-sheet degrade reason (captured live): `expo-sqlite web (wa-sqlite/OPFS) init failed: Sync operation timeout`.
- Root cause (measured, not guessed): `src/sync/persistence.web.ts` probes the synchronous channel at engine boot (`storage.getItemSync('__sync_probe__')`). expo-sqlite's web `WorkerChannel.ts` busy-spins waiting for the worker with a budget of **1,000,000 `Atomics.pause()` iterations ≈ 24 ms measured** (fallback without `Atomics.pause`: 1e9 empty iterations ≈ 256 ms measured). `Atomics.pause` exists in Chromium 148 (= current stable Chrome). The first-ever sync op races the worker boot (worker spawn + script load + wa-sqlite WASM compile + OPFS open = hundreds of ms), so the probe **deterministically throws in any modern Chrome** — dev or deployed, headless or headed. The OPFS directory (`expo-sqlite`) IS created moments later by the worker, but the engine has already fallen back to in-memory.
- Consequence: the headline S2.8 deliverable (durable web offline; "offline edits survive a full page reload") is broken at HEAD; web would ship permanently on the R5 degraded path while claiming the flip. Phase exit criterion "OPFS persistence ATTACH" fails.
- Reproduce: flag-on web load → tap pill → sheet shows the reason string. Measurement script approach: `Atomics.pause` 1M-iteration timing in the page (24.4 ms on this machine).
- Suggested fix direction (owner: backend-specialist, `src/sync/persistence.web.ts`): warm the worker asynchronously before the synchronous probe — e.g. `await storage.getItemAsync('__sync_probe__')` (unbounded promise wait) inside an async `createSyncPersistence`, then attach the sync plugin; `initTier1Sync` is already async. Re-smoke this item after the fix.

## BLOCKER B2 (secondary) — pill can never reach "Synced" while any Tier-1 root is empty

- Sheet showed "First sync has not finished yet." indefinitely while Trips=35 rows and Places=72 rows were fully hydrated — because `trip_days`, `trip_place_comments`, `trip_packing_items` had **0 rows**.
- Mechanics: `lastSyncAgeMs` requires a non-null `lastSyncAt` on EVERY entity (`src/sync/telemetry.ts`), but `recordEntityHydrated` only fires from `obs$.onChange` (`src/sync/hydrate.ts` attachEntity) — a root whose hydration returns zero rows never changes the observable, never gets stamped. Most real users have ≥1 empty root → "Syncing…" forever even after B1 is fixed.
- Owner: backend-specialist (stamp `lastSyncAt` from the plugin's sync-state `isLoaded`/`lastSync` instead of, or in addition to, onChange).
